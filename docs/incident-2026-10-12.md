## Update and rollback improvements proposed

The existing updater stages checksum-verified releases with separate dependency environments, waits for idle, switches atomically, and retains the previous release. It rolls back if the new runtime fails backend authentication within three minutes. Credentials, mailbox and speaker settings are outside release folders.

This health gate does not prove drawing, queueing, printing or playback. Only one installed release currently exists on this Pi, so there is no present older directory to switch to. The 9 October sanitized image is a recovery fallback requiring fresh enrollment and speaker/network setup, not an immediate rollback.

Before enabling automatic updates: preserve a tested source/config recovery snapshot securely, publish uniquely versioned releases, add an explicit rollback/pin operation that prevents immediate reinstall, canary updates on one station, and test protocol compatibility with older clients. Backend rollback must use a compatible server revision and preserve database/media; destructive schema changes would prevent safe code-only rollback. The previous known functional backend candidate is the recorded 9 October deployment, but no rollback is justified by current evidence.
